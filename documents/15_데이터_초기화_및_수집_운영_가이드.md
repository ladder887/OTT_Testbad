# 15. 데이터 초기화 및 수집 운영 가이드

> 갱신일: 2026-04-16
> 목적: 재실험 전에 기존 데이터 오염을 제거하고, 라벨 기반으로 정상/공격/시나리오별 재현 가능한 수집 구조를 유지한다.
> 본 문서는 기존 라벨 삽입 설계 문서를 포함한 통합 운영 정본이다.

---

## 1. 로그만 삭제하면 충분한가?

아니다. 이 프로젝트는 데이터가 여러 저장소에 분산된다.

1. Elasticsearch: 원본 요청 로그
2. Neo4j: Detection Engine이 적재한 그래프
3. PostgreSQL: watch_history, sessions, audit_logs
4. Filebeat offset: 이미 읽은 로그 위치 레지스트리

주의:
- `watch_history`는 PostgreSQL 활동 테이블이며, `Request.kind` 분류 대상은 아니다.
- Detection의 핵심 `Request.kind`는 `playback_start`, `browse_content`, `hls_manifest`, `hls_segment` 4종으로 유지한다.

Elasticsearch만 비워도 Neo4j/DB에 이전 흔적이 남고,
Filebeat offset을 유지하면 과거 로그 재수집 여부가 의도와 다르게 동작할 수 있다.

## 1.5 라벨 수집 전체 흐름

```
WatchPage(웹/스크립트)
  -> Edge `/api` 경유로 playback/start 에 label, run_id, scenario_id 전달
  -> Edge OpenResty(Lua)에서 X-Scenario-Label 및 쿼리 파라미터 처리
  -> nginx access log(token_label) 기록
  -> Filebeat가 Elasticsearch 전송
  -> Detection(main_v5.py)가 ES 로그를 Neo4j Request.label로 적재
```

정본 규칙:

1. 정본 필드: `label`
2. 호환 별칭: `dataset_label`
3. 최종 로그 필드: `token_label`
4. Neo4j 적재 필드: `Request.label`

## 2. 권장 초기화 단위

| 대상 | 권장 동작 | 비고 |
|---|---|---|
| Elasticsearch | 수집 인덱스/데이터스트림 삭제 | `scrubber-nginx-*`, `filebeat-*`, `.ds-*` 포함 |
| Neo4j | 그래프 전체 삭제 | `MATCH (n) DETACH DELETE n` |
| PostgreSQL 활동 테이블 | TRUNCATE | `watch_history`, `sessions`, `audit_logs` |
| Filebeat offset | 필요 시 리셋 | 동일 로그 재수집이 필요할 때만 |

## 3. 로컬 초기화 스크립트

스크립트 위치:
- scripts/data/reset_collection_data.ps1

기본 실행 (ES + Neo4j):

```powershell
powershell -ExecutionPolicy Bypass -File scripts/data/reset_collection_data.ps1
```

PostgreSQL 활동 테이블까지 초기화:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/data/reset_collection_data.ps1 -ClearPostgresActivity
```

Filebeat offset까지 초기화:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/data/reset_collection_data.ps1 -ClearPostgresActivity -ResetFilebeatOffsets
```

전체 초기화 없이 Neo4j의 구식 스키마(`Video`, `FOR_VIDEO`, `PART_OF`, `FOR_CONTENT`)만 정규화:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/data/normalize_legacy_graph_schema.ps1
```

이 스크립트는 아래 작업을 순서대로 수행한다.

1. `FOR_CONTENT` -> `TARGETS_CONTENT` 마이그레이션
2. `FOR_VIDEO` 관계를 `TARGETS_CONTENT` + `Content` 노드로 변환
3. `PART_OF` 관계를 `BELONGS_TO` + `Content` 노드로 변환
4. `FOR_SEGMENT` 경유 요청의 `TARGETS_CONTENT` 보강
5. 잔여 `Video` 노드 제거

## 5. 정상/공격/시나리오 구분 수집 구조

### 5.1 필수 메타데이터

1. run_id: 수집 실행 배치 식별자 (예: `20260408_r01`)
2. scenario_id: 시나리오 식별자 (예: `N1`, `A3`)
3. label: 시나리오 라벨 (예: `normal`, `attack_A2`)
4. dataset_label: 호환용 별칭

### 5.2 playback 시작 시 메타데이터 전달

API:

```json
POST /api/playback/start
{
  "content_id": "movie_001",
  "label": "normal",
  "run_id": "20260408_r01",
  "scenario_id": "N1",
  "dataset_label": "normal"
}
```

웹 수동 테스트:

- /watch/movie_001?label=normal&run_id=20260408_r01&scenario_id=N1

호환 모드(구 파라미터):

- /watch/movie_001?dataset_label=normal&run_id=20260408_r01&scenario_id=N1

### 5.3 저장되는 필드

Gateway access log와 Detection Engine Request 노드에 아래 필드가 남는다.

1. token_run_id
2. token_scenario_id
3. token_dataset_label
4. token_label

### 5.4 권장 라벨 값

현재 구현은 영문/숫자/`_`/`-` 조합의 문자열 라벨을 허용한다.

운영 권장값:

1. `normal`
2. `attack_A1`
3. `attack_A2`
4. `attack_A3`
5. `attack_A4`
6. `attack_A5`
7. `attack_A6`
8. 필요 시 실험 확장 라벨(`attack_A7`, `attack_A8`)을 별도 런에서 사용

공격 시나리오 분류 기준은 `07`의 A1~A6 정본을 따른다.

## 6. 수집 검증 예시

Elasticsearch에서 시나리오별 건수 확인:

```http
GET scrubber-nginx-*/_search
{
  "size": 0,
  "aggs": {
    "by_scenario": {
      "terms": { "field": "token_scenario_id.keyword", "size": 20 }
    },
    "by_label": {
      "terms": { "field": "token_label.keyword", "size": 10 }
    }
  }
}
```

Neo4j에서 Request 분포 확인:

```cypher
MATCH (r:Request)
RETURN r.label AS label, r.scenario_id AS scenario, count(*) AS cnt
ORDER BY cnt DESC;
```

Neo4j에서 구식 라벨/관계 잔존 여부 확인:

```cypher
MATCH (v:Video)
WITH count(v) AS video_nodes
OPTIONAL MATCH ()-[fv:FOR_VIDEO]->()
WITH video_nodes, count(fv) AS for_video_rels
OPTIONAL MATCH ()-[po:PART_OF]->()
WITH video_nodes, for_video_rels, count(po) AS part_of_rels
OPTIONAL MATCH ()-[fc:FOR_CONTENT]->()
RETURN video_nodes, for_video_rels, part_of_rels, count(fc) AS for_content_rels;
```

정본 관계 생성 확인:

```cypher
OPTIONAL MATCH ()-[tc:TARGETS_CONTENT]->()
WITH count(tc) AS targets_content_rels
OPTIONAL MATCH ()-[bs:BELONGS_TO]->()
RETURN targets_content_rels, count(bs) AS belongs_to_rels;
```
