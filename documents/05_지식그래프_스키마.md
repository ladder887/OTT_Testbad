# 05. 지식그래프 스키마

> 운영 참고 (2026-04-16): 본 문서는 그래프 설계 기준 문서다. 실제 적재 검증/운영 확인은 `10`, `11`, `15` 문서의 실행 절차를 우선한다.

> 라이브 관련 공격 패턴은 `07_공격_시나리오.md`의 A1~A6 기준으로 해석하며,
> `Content(type=live)` 주변의 세션 시작/종료 동기화 및 IP/계정 전환 패턴을 주요 특징으로 사용한다.

## 2. 관계 정의 (11종)

```
Account ──HAS_TOKEN──→ Token
Token ──CREATES_SESSION──→ Session
Session ──FROM_IP──→ ClientIP
Session ──ON_DEVICE──→ Device
Session ──SERVED_BY──→ Edge
Session ──REFERRED_BY──→ Referrer
Session ──MAKES_REQUEST──→ Request
Request ──FOR_SEGMENT──→ Segment
Request ──TARGETS_CONTENT──→ Content
Segment ──BELONGS_TO──→ Content
Segment ──CACHED_AT──→ Edge
```

| 관계 | 출발 노드 | 도착 노드 | 속성 | 설명 |
|------|---------|---------|------|------|
| HAS_TOKEN | Account | Token | issued_at | 계정이 토큰을 보유 |
| CREATES_SESSION | Token | Session | | 토큰으로 세션 생성 |
| FROM_IP | Session | ClientIP | first_seen, last_seen | 세션의 출발 IP |
| ON_DEVICE | Session | Device | | 세션의 디바이스 |
| SERVED_BY | Session | Edge | | 세션을 처리한 Edge |
| REFERRED_BY | Session | Referrer | | HTTP Referer 출처 |
| MAKES_REQUEST | Session | Request | sequence_num | 세션 내 요청 순서 |
| FOR_SEGMENT | Request | Segment | | 요청한 세그먼트 |
| TARGETS_CONTENT | Request | Content | | playback_start/browse_content 등 API 요청의 대상 콘텐츠 |
| BELONGS_TO | Segment | Content | | 세그먼트의 소속 콘텐츠 |
| CACHED_AT | Segment | Edge | cache_time | Edge에 캐시된 세그먼트 |

## 3. Neo4j Cypher 쿼리 예시

### 3.1 그래프 생성 (로그 → Neo4j)

```cypher
// Account 생성
MERGE (a:Account {user_id: $user_id})
SET a.plan_type = $plan, a.max_streams = $max_streams

// Token 생성 및 Account 연결
CREATE (t:Token {token_id: $token_id, issued_at: datetime($issued_at), 
                 expires_at: datetime($expires_at), allowed_edge: $edge})
MERGE (a:Account {user_id: $user_id})
CREATE (a)-[:HAS_TOKEN {issued_at: datetime($issued_at)}]->(t)

// Session 생성 및 Token 연결
CREATE (s:Session {session_id: $sid, start_time: datetime($start), label: $label})
MERGE (t:Token {token_id: $token_id})
CREATE (t)-[:CREATES_SESSION]->(s)

// IP 연결
MERGE (ip:ClientIP {ip_address: $ip})
SET ip.region = $region, ip.asn_type = $asn_type
MERGE (s:Session {session_id: $sid})
CREATE (s)-[:FROM_IP {first_seen: datetime($ts)}]->(ip)

// Request + Segment 생성
CREATE (r:Request {request_id: $req_id, timestamp: datetime($ts), 
                   method: $method, path: $path, kind: $kind,
                   target_content_id: $target_content_id,
                   status: $status, bytes_sent: $bytes})
MERGE (s:Session {session_id: $sid})
CREATE (s)-[:MAKES_REQUEST {sequence_num: $seq}]->(r)
MERGE (seg:Segment {segment_id: $seg_id})
CREATE (r)-[:FOR_SEGMENT]->(seg)

// API 요청의 대상 콘텐츠 연결
MERGE (c:Content {content_id: $target_content_id})
CREATE (r)-[:TARGETS_CONTENT]->(c)
```

`kind` 값은 아래 네 가지로 통일한다.
- `playback_start`
- `browse_content`
- `hls_manifest`
- `hls_segment`

위 API kind(`playback_start`, `browse_content`)는 Edge/Gateway access log의 `/api` 요청에서 추출한다.
운영 중 웹/API 클라이언트가 `:3001`을 직접 호출하면 해당 kind가 누락될 수 있다.

### 3.2 이상 패턴 탐지 쿼리

```cypher
// 패턴 1: Token Fan-out (하나의 토큰에 다수 IP)
MATCH (t:Token)-[:CREATES_SESSION]->(s:Session)-[:FROM_IP]->(ip:ClientIP)
WITH t, count(DISTINCT ip) AS ip_count
WHERE ip_count > 3
RETURN t.token_id, ip_count ORDER BY ip_count DESC

// 패턴 2: 동시 시청 계정 클러스터 (같은 콘텐츠, 비슷한 시간)
MATCH (a:Account)-[:HAS_TOKEN]->(t:Token)-[:CREATES_SESSION]->(s:Session)
  -[:MAKES_REQUEST]->(rp:Request {kind: "playback_start"})-[:TARGETS_CONTENT]->(c:Content)
WHERE c.content_id = $target_content
WITH c, collect({account: a.user_id, start: rp.timestamp}) AS sessions
WHERE size(sessions) > 10
RETURN c.content_id, sessions

// 패턴 3: browse_content 요청 없이 직접 시청
MATCH (a:Account)-[:HAS_TOKEN]->()-[:CREATES_SESSION]->(s:Session)
  -[:MAKES_REQUEST]->(rp:Request {kind: "playback_start"})-[:TARGETS_CONTENT]->(c:Content)
OPTIONAL MATCH (s)-[:MAKES_REQUEST]->(rb:Request {kind: "browse_content"})-[:TARGETS_CONTENT]->(c)
WITH a, s, c, count(rb) AS browse_hits
WHERE browse_hits = 0
RETURN a.user_id, c.content_id, s.session_id

// 패턴 4: Datacenter ASN에서 접근
MATCH (s:Session)-[:FROM_IP]->(ip:ClientIP)
WHERE ip.asn_type = "datacenter"
RETURN s.session_id, ip.ip_address, ip.asn_name
```

## 4. 시나리오별 그래프 구조 비교

### 정상 시청 (N1)

```
Account(user_kr_01) ──HAS_TOKEN──→ Token(tok_001)
  Token(tok_001) ──CREATES_SESSION──→ Session(s1)
    Session(s1) ──FROM_IP──→ ClientIP(192.168.0.11) [residential]
    Session(s1) ──ON_DEVICE──→ Device(Chrome/Win10)
    Session(s1) ──SERVED_BY──→ Edge(edge-kr)
    Session(s1) ──REFERRED_BY──→ Referrer(myott.com) [legitimate]
    Session(s1) ──MAKES_REQUEST──→ Request(rp) ──TARGETS_CONTENT──→ Content(movie_001) [kind=playback_start]
    Session(s1) ──MAKES_REQUEST──→ Request(r1) ──FOR_SEGMENT──→ Seg(001)
    Session(s1) ──MAKES_REQUEST──→ Request(r2) ──FOR_SEGMENT──→ Seg(002)
    Session(s1) ──MAKES_REQUEST──→ Request(rb) ──TARGETS_CONTENT──→ Content(movie_001) [kind=browse_content]
    ...
```

특징: 단순한 선형 구조, Referrer 존재, browse_content kind 요청 존재

### 공격 A2 (토큰 로테이션)

```
Account(stolen_01) ──HAS_TOKEN──→ Token(t1) ──SESSION──→ S1 ──IP──→ IP(x1) [datacenter]
Account(stolen_02) ──HAS_TOKEN──→ Token(t2) ──SESSION──→ S2 ──IP──→ IP(x2) [datacenter]
Account(stolen_03) ──HAS_TOKEN──→ Token(t3) ──SESSION──→ S3 ──IP──→ IP(x3) [datacenter]
  ...
S1 ──MAKES_REQUEST──→ Request(p1) ──TARGETS_CONTENT──→ Content(live_001) [kind=playback_start, ts=14:00:01]
S2 ──MAKES_REQUEST──→ Request(p2) ──TARGETS_CONTENT──→ Content(live_001) [kind=playback_start, ts=14:00:03]
S3 ──MAKES_REQUEST──→ Request(p3) ──TARGETS_CONTENT──→ Content(live_001) [kind=playback_start, ts=14:00:02]
  ...
(browse_content kind 요청 없음)
(Referrer 없음 또는 비정상)

[30분 후 그래프 변화]
S1의 FROM_IP가 IP(x1) → IP(x4)로 교체
S2의 FROM_IP가 IP(x2) → IP(x5)로 교체
→ 시간에 따른 IP 로테이션 패턴
```

특징: Content 노드 중심 팬인, playback_start 시각 동기화, ASN 공통, browse_content kind 결여
