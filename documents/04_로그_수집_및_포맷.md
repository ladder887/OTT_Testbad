# 04. 로그 수집 및 포맷

> 운영 참고 (2026-04-16): 본 문서는 로그 설계 기준 문서다. 실제 운영 파이프라인 점검/복구 절차는 `11`, `15` 문서를 우선한다.

> 라이브 트래픽(정상 + A6/A4/A2 연계 공격)에서는 `playlist.m3u8` 폴링 로그가 3~6초 간격으로 반복되는 패턴이 공통적으로 관찰된다.

## 1. CDN Edge Access Log (JSON)

모든 탐지의 기반이 되는 핵심 데이터. Edge 4개 서버에서 동일 포맷으로 기록.

### 1.1 필드 정의

| 필드 | 타입 | 예시 | 설명 |
|------|------|------|------|
| timestamp | ISO8601 | "2025-07-15T14:23:45.123Z" | 요청 시각 (ms 단위) |
| client_ip | string | "192.168.0.11" | 클라이언트 IP |
| client_region | string | "KR" | VLAN 기반 지역 (라우터에서 부여) |
| edge_server | string | "edge-kr" | 응답한 Edge 서버 ID |
| method | string | "GET" | HTTP 메소드 |
| uri | string | "/content/movie_001/720p/seg_0042.ts" | 요청 경로 |
| status | int | 200 | HTTP 응답 코드 |
| bytes_sent | int | 1258000 | 전송 바이트 |
| response_time_ms | float | 12.5 | 응답 시간 (ms) |

## 2. API 요청 이벤트 (보조 데이터)

`playback_start`, `browse_content`는 별도 애플리케이션 로그 파일이 아니라
Edge/Gateway의 `/api/...` 접근 로그에서 `Request.kind`로 분류되는 신호다.
즉, 웹/클라이언트 API 호출이 Edge를 경유해야 해당 이벤트가 탐지 파이프라인(ES -> Detection -> Neo4j)에 반영된다.

```json
{
  "timestamp": "2025-07-15T14:23:40.500Z",
  "event": "login",
  "user_id": "user_kr_01",
  "client_ip": "192.168.0.11",
  "user_agent": "Mozilla/5.0 ...",
  "success": true,
  "session_id": "sess_a1b2c3"
}
```

```json
{
  "timestamp": "2025-07-15T14:23:40.800Z",
  "event": "playback_start",
  "user_id": "user_kr_01",
  "session_id": "sess_a1b2c3",
  "content_id": "movie_001",
  "assigned_edge": "edge-kr",
  "cdn_token_expires": "2025-07-15T15:00:00Z"
}
```

```json
{
  "timestamp": "2025-07-15T14:23:39.200Z",
  "event": "browse_content",
  "user_id": "user_kr_01",
  "content_id": "movie_001",
  "action": "open_detail"
}
```

`browse_content` 요청 유무는 A4(정상 모방 분산) 탐지의 핵심 단서 중 하나다.
정상 사용자: login → browse_content → playback_start
공격 봇: login → playback_start (`browse_content` 없이 바로 재생)

직접 API(`:3001`) 호출로 재생을 진행하면 서비스 기능은 동작할 수 있어도,
`browse_content`/`playback_start` 이벤트가 Edge 로그 기반 탐지 경로에서 누락될 수 있다.

## 3. 수집 파이프라인

```
사용자 API/HLS 요청
      │
      ↓
Edge-KR 로그 ──→ Filebeat ──→┐
Edge-JP 로그 ──→ Filebeat ──→├──→ Logstash ──→ Elasticsearch
Edge-SG 로그 ──→ Filebeat ──→│                      │
Edge-US 로그 ──→ Filebeat ──→┘                      │
                                                     ↓
                                          Detection Engine (Python)
                                                     │
                                              ┌──────┴──────┐
                                              │             │
                                           Neo4j       CSV/Parquet
                                         (그래프)     (ML feature)
```

### Filebeat 설정 (각 Edge 서버)

```yaml
# filebeat.yml
filebeat.inputs:
  - type: log
    enabled: true
    paths:
      - /var/log/nginx/access.log
    json.keys_under_root: true
    json.add_error_key: true

output.logstash:
  hosts: ["192.168.0.120:5044"]
```

## 4. 파생 Feature (세션 레벨)

Detection Engine이 원본 로그에서 세션 단위로 집계하여 생성하는 feature.

| Feature | 계산 방식 | 정상 범위 | 이상 단서 |
|---------|---------|---------|---------|
| seg_request_count | 세션 내 세그먼트 요청 수 | 10~400 | 매우 높으면 대량 다운로드 |
| avg_interval_sec | 세그먼트 간 평균 요청 간격 | 5.5~6.5 | <4.5이면 병렬, =6.0이면 봇 |
| interval_stddev | 요청 간격 표준편차 | 0.2~0.8 | <0.05이면 기계적 |
| has_manifest | 매니페스트 요청 존재 여부 | true | false면 직접 접근 |
| unique_resolutions | 요청한 해상도 종류 수 | 1~3 | 0이면 비정상 |
| referer_legitimate | Referer가 정상 도메인인지 | true | false면 외부 임베딩 |
| referer_empty | Referer가 비어있는 비율 | <5% | >50%면 비브라우저 |
| edge_match_ratio | 토큰 Edge와 실제 Edge 일치 비율 | 100% | <100%면 토큰 공유 |
| session_duration_sec | 세션 총 지속 시간 | 300~7200 | 매우 짧거나 매우 긺 |
| seq_monotonic | 세그먼트 번호 단조증가 비율 | 80~100% | <50%면 비순차 |
| has_browse_content_request | API에서 `browse_content` 요청 존재 | true | false면 봇 의심 |
| concurrent_sessions | 동일 계정의 동시 활성 세션 수 | 1~2 | 플랜 초과면 공유 |
| ip_asn_type | IP의 ASN 유형 | residential | datacenter면 의심 |
