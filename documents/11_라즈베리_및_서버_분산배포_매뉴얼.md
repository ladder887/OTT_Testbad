# 11. 라즈베리 및 서버 분산배포 매뉴얼 (물리 분리형 실행본)

이 문서는 현재 저장소 기준으로 **서버 3대 + Edge Pi 4대 + Client Pi 10대**를 실제 배포하는 절차를 단계별로 정리한 실행 매뉴얼이다.

---

## 0. 목표 구성

- 서버#1 (192.168.0.100): API + Origin + Postgres + 웹 UI
- 서버#3 (192.168.0.120): Neo4j + Elasticsearch + Kibana
- 서버#4 (192.168.0.130): Detection Engine (Elasticsearch poll -> Neo4j 적재)
- Edge Pi 4대: edge-kr/jp/sg/us 각각 1대씩 물리 분리
- Client Pi 10대: 클라이언트/공격자 역할

현재 저장소에 서버/엣지별 compose 파일을 추가해 두었다.

- deploy/server1/docker-compose.yml
- deploy/server3/docker-compose.yml
- deploy/server4/docker-compose.yml
- deploy/edge-kr/docker-compose.yml
- deploy/edge-jp/docker-compose.yml
- deploy/edge-sg/docker-compose.yml
- deploy/edge-us/docker-compose.yml

`deploy/server2`는 과거 임시 통합형 구성으로 **폐기(Deprecated)** 되었으며, 현재 운영에서는 사용하지 않는다.

Client Pi 상세 운용 카드는 `12_라즈베리_개별_운용_설명서.md`를 참고한다.
Edge Pi 상세 운용 카드는 `13_엣지_라즈베리_개별_운용_설명서.md`를 참고한다.

### 1.3 Git 없이 XFTP로 배포하는 방법

Git 저장소를 서버에서 직접 받을 수 없다면, 로컬 PC에서 XFTP로 필요한 폴더만 업로드해도 된다.

중요 원칙:

1. 모든 장비에서 배포 루트 경로를 동일하게 맞춘다. (권장: `~/OTT_Testbad`)
2. `deploy/.../docker-compose.yml`에서 참조하는 상대경로(`../../...`)가 깨지지 않게 폴더 구조를 유지한다.

### 1.4 인터넷 제한(오프라인) 환경일 때

각 장비가 Docker Hub/Elastic Registry에 접근할 수 없다면, 이미지까지 함께 옮겨야 한다.

절차 요약:

1. 로컬 빌드 장비에서 필요한 이미지를 `docker save`로 tar 생성
2. XFTP로 tar 파일 전송
3. 각 장비에서 `docker load -i <image.tar>` 실행
4. 이후 `docker compose up -d` 실행

오프라인 환경이면 2, 3, 4번을 장비별로 먼저 끝낸 뒤 본 문서의 서버/Edge 기동 순서를 따른다.


참고:

- 플랫폼 `/manage`에서 VOD `sourceVideo`를 업로드하면 `scrubber-api`가 FFmpeg로 `origin/hls/<hls_path>/`에 1080p/720p와 `master.m3u8`를 자동 생성한다.
- 자동 생성은 `content_type=vod`에서만 수행되며, 라이브(`live`)는 기존처럼 `origin/source/sample.mp4` 기반 `live-encoder` 경로를 사용한다.
- `scrubber/api` 코드 변경 후에는 서버#1에서 `docker compose up -d --build scrubber-api`로 API 이미지를 반드시 재빌드해야 자동 생성 로직이 반영된다.
- `origin/web` 코드 변경 후에는 서버#1에서 `docker compose up -d --build origin-web`로 웹 이미지를 반드시 재빌드해야 한다.
- 탐지 관측 기준으로는 `origin-web`의 `VITE_API_URL`이 반드시 Edge URL(`http://192.168.0.111` 등)을 바라봐야 하며,

## 9. 트러블슈팅

1. 특정 Edge에서 403/503 발생
- 서버#1 API 헬스(내부) 확인: `curl http://192.168.0.100:3001/health`
- 해당 Edge Pi 로그 확인: `docker logs edge-kr --tail 200`

2. Kibana에서 로그 안 보임
- Data View가 `scrubber-nginx-*`인지 확인
- 시간 범위를 Last 24 hours로 변경
- 해당 Edge Pi Filebeat 로그 확인: `docker logs filebeat-edge-kr --tail 200`

3. Neo4j 적재가 안 됨
- 서버#4 detection 로그 확인: `docker logs ott-detection-engine-central --tail 200`
- 서버#3 7687 포트 확인

4. 영상 요청이 403으로 막힘 (master.m3u8, ts)
- 증상: `/api/playback/start` 응답의 `edge`가 `edge-local`인데 실제 요청 Edge는 `edge-kr/jp/sg/us`로 나감
- 원인: region 미매칭(예: UNKNOWN) 시 기본 edge ID와 기본 edge URL이 서로 다른 값으로 선택되어 `edge_mismatch` 발생
- 조치: 서버#1의 기본 Edge 값을 명시적으로 맞춘다.
	- `deploy/server1/docker-compose.yml`에서 `EDGE_DEFAULT_ID`와 `EDGE_DEFAULT_URL`을 동일 Edge로 설정
	- 적용 후 서버#1에서 `docker compose up -d --build scrubber-api` 재실행

5. 시청은 되는데 Neo4j 지식그래프가 비어 있음
- 1차 확인(Edge Pi):
	- `docker logs filebeat-edge-kr --tail 200`
	- `docker exec -it filebeat-edge-kr filebeat -strict.perms=false test output`
	- `docker exec -it filebeat-edge-kr filebeat -strict.perms=false test config`
	- 참고: `filebeat test output`를 옵션 없이 실행하면 `filebeat.yml` 소유권(strict perms) 검사 오류가 날 수 있다.
	- 로그에 아래와 같은 경고가 보이면 매핑 충돌 상태다.
		- `document_parsing_exception: object mapping for [service] tried to parse field [service] as object, but found a concrete value`
	- 조치: `deploy/edge-common/filebeat.yml`에서 `fields.service`를 커스텀 키(예: `edge_service`)로 변경 후 filebeat 재기동
- 2차 확인(서버#3 Elasticsearch):
	- `curl http://192.168.0.120:9200/_cat/indices?v | egrep 'scrubber-nginx|filebeat'`
	- 인덱스가 없으면 `deploy/edge-common/filebeat.yml`의 index/ILM 설정 반영 후 Edge Pi 재기동
- 3차 확인(서버#4 Detection):
	- `docker logs ott-detection-engine-central --tail 200`
	- `docker exec -it ott-detection-engine-central env | grep NEO4J_DATABASE` (권장값: `neo4j`)
	- 정상 로그 예시:
		- `Read N new log entries from Elasticsearch`
		- `Processed nodes: {...}`
	- 에러가 보이면 즉시 재기동:
		- `cd ~/OTT_Testbad/deploy/server4 && docker compose up -d --build detection-engine`
	- 로그에 `Read 0 new log entries from Elasticsearch`가 반복되면 `ELASTICSEARCH_INDEX` 값과 실제 인덱스명을 대조
	- 권장값: `scrubber-nginx-*,filebeat-*,.ds-scrubber-nginx-*,.ds-filebeat-*` (존재하지 않는 정확 인덱스명 혼합 금지)
	- `_count`는 0이 아닌데 detection만 0건이면, 최신 detection 이미지로 재빌드하여 부트스트랩 조회(match_all fallback)가 포함된 버전을 적용
		- `cd ~/OTT_Testbad/deploy/server4 && docker compose up -d --build detection-engine`
	- 최신 버전 진단 로그에서 아래 3줄을 같이 확인
		- `ES search target resolved: patterns=..., resolved_count=...`
		- `ES self-check count(match_all) on '...': N`
		- `Bootstrap match_all also returned 0 hits` 또는 `... found N hits`
	- 최신 엔진은 count>0인데 range/match_all이 0일 때 `_doc` 정렬 백필을 자동 수행하며, 로그에 아래 문구가 뜨면 정상 복구 경로다.
		- `Range/bootstrap returned 0 but doc-sort fallback found N hits`
	- 아래 명령 결과가 `OLD_IMAGE_OR_OLD_CODE`면 서버#4 컨테이너가 구버전 코드로 떠 있는 상태다.
		- `docker exec -it ott-detection-engine-central sh -lc "grep -n 'ES search target resolved' /app/main.py || echo OLD_IMAGE_OR_OLD_CODE"`
	- 이 경우 서버#4 호스트 소스 반영 여부부터 확인:
		- `grep -n 'ES search target resolved' ~/OTT_Testbad/detection/engine/main_v5.py || echo HOST_CODE_OLD`
	- `HOST_CODE_OLD`면 XFTP/rsync로 `detection/engine/`을 서버#4에 다시 업로드 후 아래 순서로 강제 재빌드:
		- `cd ~/OTT_Testbad/deploy/server4`
		- `docker compose down`
		- `docker compose build --no-cache detection-engine`
		- `docker compose up -d --force-recreate detection-engine`
- 3.5차 확인(서버#3 Neo4j):
	- Browser에서 `:use neo4j` 실행 후 조회 (system DB에 있으면 그래프가 비어 보일 수 있음)
	- 카운트 확인:
		- `MATCH (n) RETURN count(n);`
	- 서버 쉘에서 직접 확인:
		- `docker exec -it ott-neo4j cypher-shell -d neo4j -u neo4j -p ott_detection_2025 "MATCH (n) RETURN labels(n)[0] AS label, count(*) AS cnt ORDER BY cnt DESC;"`
- 4차 조치:
	- Filebeat 레지스트리 초기화가 필요하면 아래 순서를 정확히 실행
		- `cd ~/OTT_Testbad/deploy/edge-kr`
		- `docker compose stop filebeat`
		- `docker compose rm -f filebeat`
		- `docker volume rm ott-edge-kr_filebeat_data`
		- `docker compose up -d filebeat`
	- 볼륨 삭제가 `volume is in use`로 실패하면, 해당 볼륨을 붙잡고 있는 컨테이너를 먼저 삭제해야 한다.
		- `docker ps -a --filter volume=ott-edge-kr_filebeat_data`
	- 재기동 후 테스트 트래픽 생성(로그가 남는 경로) 후 카운트 재확인
		- `for i in 1 2 3 4 5; do curl -s "http://192.168.0.111/?probe=$i" >/dev/null; done`
		- 참고: `/health`는 edge nginx 설정에서 `access_log off`라 로그가 생성되지 않는다.
		- `curl "http://192.168.0.120:9200/scrubber-nginx-*,.ds-scrubber-nginx-*/_count?ignore_unavailable=true&pretty"`
	- 서버#4에서 `docker compose up -d --build detection-engine`

6. `hls_manifest`/`hls_segment`만 보이고 `playback_start`/`browse_content`가 누락됨
- 증상: 시청은 정상인데 Neo4j `Request.kind`가 HLS 2종만 반복됨
- 원인: 웹/API 클라이언트가 Edge(`/api`) 대신 `:3001`을 직접 호출해 API 요청이 Edge 로그 수집 경로를 우회함
- 조치:
	- 서버#1 `deploy/server1/docker-compose.yml`의 `origin-web`에서 `VITE_API_URL`을 Edge URL로 설정
	- 로컬 모드에서는 `docker-compose.lab.yml`의 `origin-web`, `scrubber-console` `VITE_API_URL`을 `http://localhost:8081`로 유지
	- 변경 후 웹 컨테이너 재빌드: `docker compose up -d --build origin-web`

## 10. 왜 구조를 바꿨는가

이전 버전은 빠른 검증을 위해 edge 4개를 1대에서 포트 분리로 운용했다.
지금 버전은 실증 목적(물리 분리/장비 독립 장애 분석)에 맞춰 아래처럼 수정했다.

- edge-kr/jp/sg/us를 서로 다른 Edge Pi로 분리
- Detection Engine을 별도 서버로 분리
- 로그 수집은 각 Edge Pi의 Filebeat -> 중앙 Elasticsearch로 통합
