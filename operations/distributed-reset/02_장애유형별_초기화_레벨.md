# 02. 장애유형별 초기화 레벨

초기화를 매번 전체로 하면 시간이 오래 걸리고 오탐 원인 분석이 어려워진다.
아래처럼 증상별 최소 범위만 초기화한다.

| 레벨 | 적용 상황 | 수행 범위 |
|---|---|---|
| L1 | 라벨/시나리오 혼합, 과거 로그 잔존 | ES 인덱스 삭제 + Neo4j 삭제 + Detection 재기동 |
| L2 | 사용자 세션/이력까지 오염 | L1 + PostgreSQL 활동 테이블 TRUNCATE |
| L3 | Filebeat가 과거 포인터로 누락/중복 수집 | L2 + Edge filebeat offset 볼륨 리셋 |
| L4 | 저장소 자체 이상/복구불가 | 컨테이너 down 후 데이터 볼륨 삭제 재생성 |

---

## 레벨 선택 가이드

1. Kibana에는 데이터가 있는데 Neo4j만 이상하다
- L1 우선

2. 로그인/세션 상태까지 꼬여 시나리오 재현이 안 된다
- L2

3. Edge access.log는 늘어나는데 ES 유입이 없거나 중복이 심하다
- L3

4. Elasticsearch/Neo4j 자체가 깨진 상태로 부팅 실패
- L4 (최후 수단)

---

## 절대 비권장 패턴

1. 서비스 실행 중 DB 내부 파일을 직접 삭제
2. PostgreSQL data 디렉토리에 빈 파일 덮어쓰기
3. Neo4j /data를 임의로 rm 후 즉시 재기동
4. ES data 경로를 컨테이너 내부에서 수동 정리

이 방식은 단기적으로 비워져 보여도, 장기적으로 인덱스/트랜잭션 손상을 만든다.

---

## L4 수행 시 최소 안전 순서

1. 해당 스택 중지 (docker compose down)
2. 관련 named volume 삭제
3. 스택 재기동 (docker compose up -d)
4. 초기 카운트 점검 후 수집 시작

항상 L1 -> L2 -> L3 순서로 올리고,
L4는 마지막 대안으로만 사용한다.
